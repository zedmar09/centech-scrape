# Laravel Flexepos Fallback Integration Plan

## Goal

Use the deployed `centech-scrape` service to retrieve Flexepos financial data
when the Laravel backend does not receive complete POS data files.

The normal POS import remains the primary source. Flexepos scraping only fills
missing store/date records and must never overwrite newer official POS data.

## Proposed architecture

```text
Missing POS data detected
        |
        v
Laravel creates fallback run and jobs
        |
        v
Laravel queue worker calls secured centech-scrape endpoint
        |
        v
Next.js + Playwright + Browserless scrape Flexepos
        |
        v
NDJSON job results stream back to Laravel
        |
        v
Laravel validates and upserts fallback financial rows
```

Laravel owns:

- fallback run and job records;
- detection of missing POS data;
- queueing, retries, pause, resume, and cancellation;
- final financial rows and source precedence;
- user authorization and audit history; and
- status APIs consumed by the Next.js frontend.

`centech-scrape` owns:

- Browserless and Playwright connections;
- Flexepos authentication;
- isolated Flexepos sessions;
- report navigation and parsing; and
- returning normalized category rows.

## Why the scraper endpoint uses batches

A full month contains approximately:

```text
84 stores × 30 dates = 2,520 Sales jobs
```

That cannot run in one Vercel request. Browserless and the deployed server
function have sub-minute limits.

Laravel must split work into short batches:

```text
Maximum six store/date jobs per Sales request
Maximum two concurrent scraper requests
```

The current Sales implementation uses:

```text
2 Browserless connections
× 3 isolated Flexepos contexts
= 6 stores concurrently
```

The concurrency limit must be global. The website and Laravel must not each
start two additional Browserless requests at the same time.

## Phase 1: secure the scraper endpoints

The externally reachable endpoints must not be anonymous. An anonymous user
could otherwise consume Browserless units and use stored Flexepos credentials.

Configure the same random secret in both deployments:

```env
FLEXEPOS_SCRAPER_API_TOKEN=<long-random-secret>
```

Laravel sends:

```http
Authorization: Bearer <long-random-secret>
```

The scraper must use constant-time token comparison and return:

```http
401 Unauthorized
```

when the token is missing or incorrect.

Additional endpoint protections:

- accept only `century` and `century_austin`;
- accept only configured store numbers;
- require ISO dates;
- reject end dates before start dates;
- enforce the maximum jobs per request;
- reject unexpectedly large request bodies;
- do not return Flexepos or Browserless credentials;
- log a request ID, not the authorization token; and
- optionally restrict traffic to a known proxy or IP when infrastructure
  supports a stable Laravel egress address.

## Phase 2: stable scraper API contract

### Sales

```http
POST /api/internal/flexepos/sales
Authorization: Bearer <token>
Content-Type: application/json
Accept: application/x-ndjson
```

Request:

```json
{
  "request_id": "01K0ABC123",
  "jobs": [
    {
      "job_id": "01K0JOB001",
      "organization": "century",
      "business_date": "2026-07-01",
      "store_number": "2006",
      "attempt": 1
    }
  ]
}
```

The endpoint should keep accepting a maximum of six Sales jobs. `job_id` is
generated by Laravel and returned unchanged in every event.

Response content type:

```http
application/x-ndjson
```

Example response:

```json
{"type":"job_started","request_id":"01K0ABC123","job_id":"01K0JOB001","store_number":"2006","business_date":"2026-07-01"}
{"type":"job_completed","request_id":"01K0ABC123","job_id":"01K0JOB001","rows":[{"business_date":"2026-07-01","store_number":"2006","category_code":"subject_to_tax","category_name":"Subject to Tax","debit":null,"credit":"197.53"}]}
{"type":"session_completed","request_id":"01K0ABC123","elapsed_ms":22639}
```

### Royalties

```http
POST /api/internal/flexepos/royalties
Authorization: Bearer <token>
Content-Type: application/json
Accept: application/x-ndjson
```

Royalty jobs contain:

```json
{
  "job_id": "01K0JOB002",
  "organization": "century",
  "start_date": "2026-07-01",
  "end_date": "2026-07-20",
  "store_number": "2006",
  "attempt": 1
}
```

The existing `/api/sales-scrape` and `/api/royalties-scrape` routes can be
secured and versioned instead of adding new paths. Dedicated `/api/internal`
paths are preferable because they clearly separate server-to-server access from
browser UI calls.

## Current implementation and edge-case behavior

The dedicated Laravel-facing endpoints are implemented:

```text
POST /api/internal/flexepos/sales
POST /api/internal/flexepos/royalties
```

Both routes:

- require `Authorization: Bearer <FLEXEPOS_SCRAPER_API_TOKEN>`;
- return `503` when the deployment has no configured token;
- return `401` for a missing or incorrect token;
- require `Content-Type: application/json`;
- reject request bodies larger than 64 KB while they are being streamed;
- require one to six unique jobs;
- reject duplicate job IDs and duplicate natural store/date or store/range jobs;
- validate real calendar dates, including leap years;
- validate attempts as integers from 1 through 10;
- reject Century store `4083` and all other stores outside the committed
  Financial store configuration;
- return validation failures before opening a Browserless connection; and
- stream normalized NDJSON without buffering the complete scrape result.

An upstream timeout or connection failure can end the stream without a terminal
event for every requested job. Laravel must compare the requested `job_id`
values with the received `job_completed` and `job_failed` events. Any job
without a terminal event remains incomplete and must be requeued according to
the retry policy.

The NDJSON consumer must not assume that one HTTP chunk equals one JSON event.
It must buffer through newline boundaries and also process a final valid line
when the stream closes without a trailing newline.

### Transitional security limitation

The bearer token protects the two `/api/internal/flexepos/*` routes only. The
existing browser UI still calls `/api/sales-scrape` and
`/api/royalties-scrape`, so those legacy routes remain browser-accessible during
this transition. Moving the Financial UI to Laravel should be followed by
removing or separately protecting the legacy routes. Until then, the deployment
must not be described as having every Browserless entry point protected by the
internal token.

### Verification

The endpoint unit tests cover authentication, body limits, malformed JSON,
unsupported content types, configured-store validation, duplicate jobs,
calendar/leap-date validation, royalty range ordering, decimal normalization,
NDJSON chunk boundaries, final lines without trailing newlines, and upstream
error passthrough.

Run the checks with:

```bash
npm test
npm run lint
npx tsc --noEmit
npm run build
```

## Phase 4: Laravel queue orchestration

### Creating a fallback run

Laravel determines missing coverage from the expected organization store list
and requested date range.

For Sales:

```text
one job per missing store/date
```

For Royalties:

```text
one job per store/date range
```

Do not queue store/date jobs for which complete official POS data already
exists.

### Dispatching scraper batches

Use a Laravel queue such as Redis-backed Horizon when available.

The dispatcher should:

1. atomically claim up to six queued Sales jobs;
2. acquire a distributed Browserless connection permit;
3. call the scraper endpoint;
4. consume NDJSON incrementally;
5. persist each completed job immediately;
6. release the permit in a `finally` block; and
7. schedule another batch while queued jobs remain.

Use a Redis semaphore or cache lock so no more than two scraper HTTP requests
are active globally:

```text
flexepos-browserless-permits = 2
```

The permit must cover requests started by both automatic fallback processing
and manual UI actions.

### HTTP behavior

Laravel should configure:

- connection timeout around 10 seconds;
- request timeout slightly above the deployed function maximum;
- streaming response handling;
- no automatic retry of the whole POST by the HTTP client; and
- an idempotent Laravel `job_id` for every requested job.

If the connection ends without a terminal event for a job, return that job to
the queue rather than assuming it completed.

## Phase 5: ingesting completed data

For each `job_completed` event:

1. verify `job_id`, organization, store, and period against the claimed job;
2. validate every category code against the allowed report template;
3. parse amounts as decimals, never floating-point values;
4. reject a row where both debit and credit are populated unless the category
   explicitly permits it;
5. calculate total debit, total credit, and difference in Laravel;
6. save all rows and mark the job completed in one database transaction; and
7. store `source = flexepos_scrape` and the scrape run ID.

Insert rows in batches with `upsert()`. Do not use `updateOrCreate()` once per
row.

Example:

```php
foreach (array_chunk($rows, 500) as $batch) {
    FinancialReportRow::upsert(
        $batch,
        [
            'organization',
            'report_type',
            'business_date',
            'store_number',
            'category_code',
        ],
        [
            'category_name',
            'debit',
            'credit',
            'source',
            'source_run_id',
            'updated_at',
        ],
    );
}
```

## Source precedence and late POS files

The source rule must be explicit:

```text
Official POS data > Flexepos fallback data
```

Recommended behavior:

1. Flexepos rows fill a store/date only when official POS data is missing.
2. If the official POS file arrives later, import it normally.
3. Mark the prior Flexepos rows superseded or archive them.
4. Queries and reports use the active official POS rows.
5. Keep the fallback run ID for audit and comparison.
6. Never let a later fallback retry overwrite official POS data.

Laravel should compare late POS rows with fallback rows and record discrepancies
for review before superseding them.

## Retry, pause, resume, and cancellation

Automatic retry policy:

```text
1 initial attempt + 1 automatic retry
```

After the second failure, leave the job Failed until an authorized user chooses
Retry Failed.

Pause:

- active scraper requests finish;
- no new batches are claimed.

Resume:

- queued jobs become dispatchable again.

Cancel:

- queued jobs become cancelled;
- active HTTP requests are cancelled when supported;
- late responses from cancelled jobs are ignored or stored only for audit.

Recovery:

- update job heartbeat while streaming;
- periodically detect stale `running` jobs;
- return stale jobs to `queued` when attempts remain; and
- mark them failed after the retry limit.

## Phase 6: Next.js frontend integration

The Financial UI should eventually stop owning durable runs in IndexedDB.

Replace browser-local operations with Laravel APIs:

```http
POST   /api/financial/fallback-runs
GET    /api/financial/fallback-runs
GET    /api/financial/fallback-runs/{run}
POST   /api/financial/fallback-runs/{run}/pause
POST   /api/financial/fallback-runs/{run}/resume
POST   /api/financial/fallback-runs/{run}/cancel
POST   /api/financial/fallback-runs/{run}/retry-failed
DELETE /api/financial/fallback-runs/{run}
GET    /api/financial/fallback-runs/{run}/rows
```

The existing UI can remain largely unchanged:

- filters create a Laravel run;
- Scrape Activity reads paginated Laravel jobs;
- status badges use Laravel run counters;
- Previous Runs reads Laravel history;
- result search and pagination query Laravel;
- CSV and JSON exports can be generated by Laravel; and
- switching pages or devices no longer loses run state.

The browser must not receive the internal scraper token.

## Failure cases to test

- invalid or missing bearer token;
- unsupported organization or store;
- malformed dates;
- more than six Sales jobs;
- Browserless returns `429`;
- Browserless session closes before every job finishes;
- one isolated Flexepos context fails while others succeed;
- Flexepos authentication fails;
- Flexepos returns a different store or date;
- parser rejects an unexpected table value;
- duplicate `job_completed` event;
- Laravel loses connection after some results were saved;
- Laravel worker crashes while holding a concurrency permit;
- user pauses or cancels during an active batch;
- official POS data arrives while fallback scraping is running; and
- official POS data arrives after fallback rows are active.

## Rollout plan

### Stage 1: endpoint security

- add bearer-token authentication;
- add strict request validation;
- keep existing UI behavior;
- verify Vercel runtime contains `playwright-core`.

### Stage 2: Laravel manual integration

- add run/job/result tables;
- add Laravel queue batch caller;
- expose a manual fallback-run action;
- test one date and two stores;
- compare rows with `centech-scripts`.

### Stage 3: controlled full-date runs

- test one date for all Century stores;
- confirm global two-request concurrency;
- verify retries and incomplete-stream recovery;
- compare debit/credit values and categories.

### Stage 4: automatic fallback

- detect missing POS coverage;
- create fallback runs automatically after an agreed waiting period;
- notify users that fallback data is being used;
- reconcile when late POS files arrive.

### Stage 5: move UI persistence to Laravel

- replace IndexedDB run history;
- use Laravel pagination and status APIs;
- retain IndexedDB only as an optional temporary display cache.

## Definition of done

- scraper endpoints require a valid internal token;
- Laravel can create and persist a fallback run;
- no more than two Browserless requests run globally;
- every requested job reaches a terminal state;
- incomplete streams are safely requeued;
- completed rows are inserted with decimal precision;
- official POS data always takes precedence;
- late POS files supersede fallback data safely;
- run history and errors are visible in the Financial UI;
- CSV/JSON exports reflect Laravel's stored active data; and
- one full-date run matches the authoritative `centech-scripts` output.
